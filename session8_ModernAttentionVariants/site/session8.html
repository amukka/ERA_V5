Session 8

Modern Attention
Variants

Session 7 turned every token into a vector of width D. Attention is the first place those tokens start talking to each other. We build the ordinary version first — then ask what breaks when the context gets long.

02 · the mechanism

Attention

We have used the word attention since Session 1 and deliberately not built it. Now we will. One token enters the layer as a vector x, and the layer makes three different projections of that same vector. 

             ┌── Wq ──> query
x ───────────┼── Wk ──> key
             └── Wv ──> value

Why three? Because looking for information and giving information are different jobs.

  • query — what am I looking for?
  • key — what kind of information do I contain?
  • value — what should I give you if you choose me?

Take the sequence The cat sat on the mat. When the model processes sat, its query may strongly match the key for cat, because knowing who sat matters. If that match is strong, more of cat's value flows into the representation for sat. That is attention in one sentence: each token asks a question, every other token advertises what it contains, and the best matches contribute the most information.

Attention(Q, K, V) = softmax( Q Kᵀ / √dk ) V

Read it from the inside out:

  • Q Kᵀ compares every query with every key and produces the score matrix.
  • Dividing by √dk keeps those scores from growing too large as the query/key width increases.
  • softmax runs across each query's row, turning it into positive weights that add to one.
  • Multiplying by V uses those weights to combine the value vectors.

For a decoder there is one extra rule — the causal mask. M is 0 where attention is allowed and −∞ for a future token, added before softmax, so every forbidden position receives weight zero.

CausalAttention(Q, K, V) = softmax( Q Kᵀ / √dk + M ) V

During training we want the whole sequence processed in parallel, so we do not physically stop the computation at each token. We set every forbidden future score to −∞ before softmax, and because softmax(−∞) = 0 the future receives exactly zero attention. That is what lets us train on the whole sequence at once while preserving left-to-right generation.

Two facts from this section will matter for the rest of the session.

Fact 1: every token is compared with every other token. Six tokens give 36 scores. Six hundred give 360,000. Ten thousand give one hundred million. This exact all-to-all comparison is both the strength and the cost of attention.

Fact 2: attention itself does not know token order. If token 0 and token 4 contain the same word and enter with the same vector, their Q, K and V projections are identical too. Something else has to say which came first — that is §8.

03 · the cost

The two bills attention sends

The 6 × 6 score matrix looks harmless because six is small. The first problem appears when the context grows: every new token has more other tokens to compare with. 

T = 1,000   →       1,000,000 query-key scores
T = 10,000  →     100,000,000 scores
T = 100,000 →  10,000,000,000 scores

That is the first bill: compute. Pairwise attention work grows roughly as T². Double the context and this part becomes about four times larger.

There is a second bill, and it belongs to a different moment — generation. When a model writes a reply one token at a time it has already computed the key and value for the earlier tokens. Throwing those away and recomputing them every step would be wasteful, so it keeps them. That growing list is the KV cache.

Model weights are a useful comparison. They are mostly fixed: load them once and many users share them. A KV cache is not shared — each active conversation owns its own. So a longer context creates two separate engineering questions: does attention become too expensive to compute, or does the saved conversation history become too large to store?

This widget introduces only the two growth patterns. The full cache bill — layers, KV heads, head dimension, bytes per number and concurrent users — is §10, once the cache itself has become familiar.

04 · the first lever

What happens if you remove the softmax

Start with one strange question: what if we remove the softmax? Forget production architectures for a moment — this is a small arithmetic experiment. One query, three old key-value pairs. 

query q = 2

key k₁ = 0.5    value v₁ = 10
key k₂ = 1.0    value v₂ = 20
key k₃ = 1.5    value v₃ = 30

Compare the query with each key — 2×0.5 = 1, 2×1.0 = 2, 2×1.5 = 3 — and without softmax, use those scores directly on the values: 1×10 + 2×20 + 3×30 = 140.

Now change only the order of operations. Every term contains the same q, so factor it out: 

direct:     (q×k₁)×v₁ + (q×k₂)×v₂ + (q×k₃)×v₃

factored:   q × (k₁v₁ + k₂v₂ + k₃v₃)
                 └────────  S  ────────┘

The part inside the brackets never mentions the query, so it can be computed while the old tokens arrive: S = 0.5×10 + 1.0×20 + 1.5×30 = 70. The new query then reads only S: 2 × 70 = 140. Both routes return exactly the same answer.

That precomputed S is the running state. Instead of a growing list of key-value pairs we continually update one object, S = S + key×value. With real vectors S is a matrix rather than a single number, and the same distributive rule applies:

direct: y = Σ (q · kⱼ) vⱼ     regrouped: S = Σ vⱼ kⱼᵀ ,   y = S q
after 10 tokens        → one 4×4 matrix
after 1,000 tokens     → one 4×4 matrix
after 1,000,000 tokens → one 4×4 matrix

Now put softmax back. The scores [1, 2, 3] get exponentiated to [2.72, 7.39, 20.09], and every one is divided by the shared total 30.20. The important part is not the new answer of 25.8 — it is that denominator. To find the weight of key 1 you need the scores of keys 2 and 3. Change one score and all three weights change.

That is what it means to say softmax ties the scores together. A different query creates different scores, a different denominator and different weights for every key, so exact softmax attention needs the individual old keys still available when each new query arrives.

The conclusion is not that softmax was bad. It made weights positive, made them sum to one, created competition between keys, and gave every query a fresh distribution over exact old keys. Removing it gives up all four guarantees and buys a fixed-size state with linear sequence work. Practical linear-attention systems add some of that behaviour back through feature maps, explicit normalisation, gates and decay.

05 · the cost of that trade

A new state can still carry the old contribution

The previous section compressed the past into one fixed-size state. Think of that state as a small scratchpad with two jobs: WRITE connects a clue to an answer, and READ uses the clue to recover it.

Write key A → old answer and a read with key A returns it. So the state can act as a memory. But later the answer changes — key A → new answer — and the new answer should replace the old one. Look at how the update is actually calculated: 

new state = old state + new write

After the update there is only one matrix. But its numbers were computed starting from the old state, so the old association's contribution is still inside the sum. If key A currently returns 40 and should now return 55, an add-only write gives: 

new read for A = 40 + 55 = 95   ← not 55

Three things are worth separating:

  • There is only one current matrix after each write — never two records.
  • Its fixed size is not the problem; the matrix never needed to grow.
  • The add-only write rule always carries the old contribution forward. It has no correction term to cancel what is no longer wanted.

A useful memory must do more than remember new information. It must also know how to correct old information. The next section gives the state that missing ability: read the old answer first, then write only the difference.

06 · the fix

The delta rule: write only what needs to change

The arithmetic is simple. It matters because a fixed-size attention state has to be able to update its memory, not merely pile up more information.

Key A currently returns 40, and the answer should now be 55. Adding the complete new answer repeats §5's mistake — 40 + 55 = 95. The delta rule measures the gap first: 

current answer:     40
wanted answer:      55
correction (delta): 55 − 40 = 15

write the correction: 40 + 15 = 55

That is the whole rule: read what memory says, find the difference, and write only that difference.

Why does this matter for attention? Removing softmax gave us a compact state, but an add-only state could not revise an old association. The delta rule turns that state into an updateable memory — and note that a correction can be negative, so the rule can remove information as well as add it. Modern variants also learn how strongly to write, or when old information should fade, but those are later refinements rather than new ideas.

The delta rule is much older than attention — it is Widrow–Hoff, 1960. Its use inside a linear-attention state is the 2021 fast-weight-programmers work, and making it trainable in parallel over a long sequence took until 2024 (DeltaNet). The idea was never the hard part; the efficient kernel was.

07 · the other lever

Do not look at everything

Linear attention changed the kind of memory the model uses. Sparse attention takes a different route entirely: keep normal softmax attention, but let each query use only a small number of keys. 

compare the query with the candidate keys
                    ↓
             keep the best k
                    ↓
apply softmax to those k scores and combine those k values

If k is much smaller than the context length T, the final calculation uses far fewer value vectors — k instead of T. This works when most of the useful attention is concentrated on a few tokens, but that is an empirical property, not a guarantee: some queries need evidence from many places, and dropping a useful key changes the answer.

There is a catch hidden in the phrase keep the best k: how do we know which keys are best? The naive method scores every key, sorts, and only then keeps the top k. That reduces the work after selection but not the cost of scoring every candidate — so if scoring was the expensive part, naive top-k has not solved the main problem.

Practical systems need a cheaper proposal step: a local window, a learned router, or a compressed index that suggests where to look, with exact attention running only on those candidates. The real trade-off is cheaper candidate search versus the risk of failing to propose a useful key. Sparse attention is not simply full attention with most entries deleted.

08 · position

Position, and the part that is usually skipped

§2 left one problem unresolved. The query–key dot product compares the content of two token vectors. By itself that number does not say whether the tokens are next to each other or hundreds of positions apart.

The causal mask handles one part of order — it stops a token reading the future. But among the tokens it is allowed to see, the dot product still needs a clue about distance. Imagine the same word appearing twice: 

position 2  → "bank"
position 20 → "bank"

If both occurrences produce the same key vector, a content-only comparison cannot tell which one is nearby. Position has to become part of the query–key comparison itself.

Rotary position embedding (RoPE) does this with rotation. Take two dimensions of a query or key and view them as one arrow on a 2D plane. Choose a small angle θ per step of the sequence, then rotate each token's arrow by its position × θ — so a query at position i turns by iθ and a key at position j turns by jθ.

The useful part appears in the dot product, which depends on the angle between the two arrows. Both absolute rotations cancel and only their difference survives:

R(iθ)q · R(jθ)k   =   q · R((j − i)θ)k

So the positional part of the score depends on i − j — the distance. Move both tokens ten places forward and both arrows turn further, but they turn together, so the angle between them is unchanged. RoPE turns relative token distance into relative rotation inside the attention score.

The implementation detail people often miss: a real head has more than two dimensions, so RoPE groups them into 2D pairs and rotates each pair at a different rate. That lets one head represent distance at several scales at once. Not every dimension has to be rotated either — DeepSeek-V4 applies RoPE to the last 64 dimensions and leaves the rest unchanged.

There is a boundary to the claim. Because RoPE computes rotations from a function, it has no finite lookup-table wall — the function can be evaluated at a position beyond the training length. That does not prove the model will behave well there. §9 is that separate problem.

09 · extension

DroPE, and how eight thousand became two hundred and fifty-six thousand

RoPE solved one positional problem: it replaced a finite lookup table with a rotation that can be calculated at any token position. But being calculable is not the same as working well.

Take a model trained only on sequences up to 8K. We can still ask RoPE for the rotation at position 256K, and the formula will return an answer. That tells us one thing: 

the positional rule is defined at 256K

It does not tell us this:

the model can use a 256K context reliably

The second claim is about the whole trained model. Every layer learned to operate with the positional patterns it met inside 8K. Far beyond that range the rotations may repeat, or combine in ways the model never learned to interpret. Long-context extension needs evidence.

This is where DroPE appears in the V4 record: trained at 8K, reported at 256K, a 32× extension, with positional recalibration applied before annealing. That last detail matters — it means the positional behaviour changed while the model still had training steps and learning rate available to adapt. DroPE is not a switch flipped at inference time.

Evidence boundary. The record establishes that V4 trained at 8K, reportedly reached 256K, and used a step called DroPE before annealing. It does not establish the exact DroPE algorithm or which rotary dimensions it changes — anything more detailed is a hypothesis until checked against the reference implementation. A reported extension factor is evidence for that specific model and procedure, not a promise that every model or every longer target will work.

10 · the memory bill

The cache bill, done properly

§3 introduced the KV cache as the saved keys and values from earlier tokens. Now we can calculate exactly how much memory that history needs. Start with one token in one layer: it stores one key and one value. That is where the leading 2 comes from.

Each vector holds head_dim numbers, and there is one pair per KV head. Every layer makes its own keys and values. Every token in the conversation left its own record behind. And every stored number occupies memory:

cache bytes per user = 2 × layers × kv_heads × head_dim × T × bytes_per_number

The formula looks long, but every factor answers a simple question:

2                 key and value
layers            each layer has its own cache
kv_heads          each KV head stores its own vectors
head_dim          numbers in each vector
T                 tokens saved for this conversation
bytes_per_number  storage used by each number

That is for one active conversation. A server handles several at once and their histories cannot be shared, so there is one more multiplier — the batch:

total = 2 × layers × kv_heads × head_dim × T × batch × bytes_per_number

For this lesson's yardstick — 48 layers, 8 KV heads, head dimension 128, bf16 — the raw cache at 32,768 tokens is ≈ 6.44 GB for one user and ≈ 51.54 GB for eight. Double the context and both double. Hold the context and double the users, and the total doubles too.

Context length sets the cache cost of one conversation. Concurrency multiplies that cost by the number of active conversations. That is the operational meaning of calling KV cache a per-user serving cost: model weights are loaded once and shared, conversation history is private to each active sequence.

This counts only the raw K and V tensors. A real inference server also needs memory for model weights, activations, temporary attention workspaces and allocator headroom — the formula explains the cache bill, it does not predict total accelerator memory by itself.

11 · the baseline

Grouped-query attention, and why it is the baseline rather than the answer

Keep your eye on just two terms of that formula: cache size ∝ kv_heads × context length. Grouped-query attention reduces the first one.

In ordinary multi-head attention every query head can have its own key and value head, so every token adds many K/V vectors to the cache. GQA keeps the separate query heads — they can still ask different questions — but lets several of them share one K/V head: 

query heads 1, 2, 3, 4  ──>  shared K/V head A
query heads 5, 6, 7, 8  ──>  shared K/V head B

Compare eight query heads in three arrangements:

MHA:  8 query heads, 8 K/V heads
GQA:  8 query heads, 2 K/V heads
MQA:  8 query heads, 1 K/V head

So why is GQA a baseline rather than the final answer? Because it changes how much we store per token, but it still stores something for every token: 

MHA cache:  8 × T
GQA cache:  2 × T
MQA cache:  1 × T

Every one of those still has a T in it. GQA lowers the slope of the line. It does not make the line stop growing. Double the context and the GQA cache still doubles; at a million tokens it still contains entries from a million positions.

GQA is a strong practical baseline because K/V sharing buys a large cache saving at a useful quality cost. But it does not solve long-context memory. The next section asks what happens if we reduce the other term — how many token positions must be stored at all.

12 · the other term

Compressing the sequence itself

§11 reduced the number of K/V heads stored for each token. But even with GQA the cache still keeps an entry for every token position. This section changes the other part of the problem: what if several nearby positions could share one stored entry? 

t1 → KV1
t2 → KV2          becomes          t1, t2, t3, t4 → compressed block 1
t3 → KV3
t4 → KV4

If every block contains m tokens, the number of long-range entries falls from roughly T to T / m. GQA stores fewer heads for each position; sequence compression stores fewer positions.

DeepSeek-V4's Compressed Sparse Attention adds a second saving. Having made the block summaries, it does not run expensive attention over every one of them — it selects only the top-k summaries that look most relevant to the current query: 

all tokens
    ↓  compress nearby tokens
fewer block summaries
    ↓  select top-k blocks
fewer expensive attention reads

These two steps reduce different costs:

  • compression → fewer entries stored
  • top-k → fewer summaries read by expensive attention

Selecting the best blocks creates the same practical question §7 raised: if we must run full attention over every block just to find the best ones, we have not saved much work. DeepSeek uses a small low-rank indexer to rank the block summaries cheaply. The indexer does not produce the final attention output — it only chooses which blocks deserve the more expensive read.

The trade-off is real. Compression can lose token-level detail, because one summary now speaks for several tokens. Approximate top-k can also miss a useful block. A real architecture must protect important recent detail and train the summaries and indexer well — the widget demonstrates the storage-and-read scaling idea, not the model's quality.

The reported DeepSeek-V4 architecture also interleaves a heavily compressed dense form with the top-k sparse form. The shared idea is the same either way: old history does not have to keep one equally expensive representation for every original token.

13 · the mixture

Schedules across depth

So far each mechanism may have sounded like a complete replacement for the others — standard attention or linear attention or sparse attention. But a deep model does not have to make that choice once for the whole network. Different layers can use different memory systems.

A fixed-state layer compresses the past into a small running state. Cheap to serve, because its memory does not grow with every earlier token — but the old sequence is no longer available token by token. A sparse-attention layer keeps keys and values and lets a query read selected earlier tokens directly. Exact access is restored, but every such layer adds a KV cache that grows with context. 

many fixed-state layers
    → process and combine information cheaply

occasional sparse-attention layers
    → revisit selected earlier tokens directly

The order of those layers is the depth schedule. LightningLM V4 used this repeating eight-layer motif, where D is a DeltaNet fixed-state layer and G is a sparse-attention layer: 

D D D G D D D G

Why not use G everywhere? More G layers give more frequent chances to read exact earlier tokens, but create more per-sequence KV cache. In the V4 configuration, changing from one sparse-attention layer per eight to eight per eight makes the KV state 8.0× larger while the estimated mixing compute rises only about 1.41×. For this configuration the main price of more G layers is serving memory, not FLOPs.

Why not use D everywhere? A fixed recurrent state is cheap, but it is a compressed summary. If every layer uses only that state, the model never gets another direct look at the exact old token representations.

V4 kept DDDGDDDG from the 1.78B seed model to the 120B run, which is meaningful evidence that the mixture works across scale. It is not evidence that six D layers and two G layers is the best possible ratio — the neighbouring schedules were never cleanly ablated. DDDGDDDG is a successful design choice, not a proven optimum. The broader lesson matters more than the exact motif: not every layer needs the same memory system, and the schedule itself is part of the architecture.

14 · across the boundary

State that outlives the window

Everything so far has described memory inside the current sequence window. Now split a very long document into chunks. Chunk 1 ends, its internal attention state is discarded, chunk 2 begins. What information crosses that boundary? Without an explicit mechanism, the answer may be: none of it.

V4 adds a Memory Stream. It carries exactly one thing forward: at the end of a chunk, take its final hidden state and use it as one summary vector for the next chunk. 

chunk 1 ──writes──> one memory vector ──nudges──> chunk 2

The vector has the same width as the model, and it does not get longer when the document does. After two chunks or two thousand, the stream is still one model-width vector — that is fixed-size, or O(1), cross-chunk state. It is also a severe compression: one vector cannot preserve every sentence from every earlier chunk, only a useful summary signal.

Two small rules make the stream practical. First, the vector is written with stop-gradient — the next chunk can read the memory during the forward pass, but its training loss cannot send gradients backward through the boundary into all previous chunks. That avoids building one enormous training graph across the complete document.

updated token = current token + scale × gate × memory

Second, each token gets a small learned gate between zero and one. A gate near 0 means this token mostly ignores the old summary; a small gate gives it a nudge; a large gate lets the old summary begin to dominate the present. It is learned because different tokens need different amounts of old information — a question referring to the previous chunk may use the stream, while an unrelated token largely ignores it.

The reported V4 injection scale starts near 0.078 and reaches about 0.391 by the 2B stage, with the average injected memory only about 6% of the current embedding magnitude. That is the right mental model: the Memory Stream is a small nudge from the previous chunk, not a copy of the old chunk and not a replacement for the current token.

15 · the system

Long context is a system, not a number

When somebody says "our model supports 256K context", that sounds like one specification. It is not. For the claim to be meaningful, several different things must work at the same time.

  1. Position must still make sense at the target length — either trained there natively, or extended successfully by DroPE, NTK-aware scaling or YaRN.
  2. The cache must fit. A theoretical 1M-token model is not useful if one sequence consumes all accelerator memory. This is where GQA, MQA and sequence compression matter.
  3. Compute must be affordable. Even if the cache fits, full quadratic attention over the whole context may be too expensive — sparse attention, top-k and linear attention live here.
  4. State outside the active window must be handled. If the system chunks documents, some mechanism may be needed to carry information forward.
  5. Training must expose the model to the behaviour we expect. "Architecture is mathematically defined at 256K" is not the same as "model has learned to use 256K well".
  6. Evaluation has to test understanding, not only retrieval. A model can find one planted sentence in a huge context while failing to combine evidence or follow long dependencies.

Context length is not one number. It is the point where position, memory, compute, training and evaluation all still work together.

There is one more dimension that matters specifically for the model we are building. Context windows are advertised in tokens. Users do not think in tokens — they have documents, code, legal files, textbooks and conversations. Session 3 showed why that difference matters: if the same meaning costs English 1× tokens and Telugu ~3×, then a fixed 256K-token window holds roughly a third as much comparable Telugu content.

The accelerator does not care — it charges per token either way. Tokenizer efficiency determines how quickly a language consumes the window; embedding and architecture choices determine what the model costs; attention determines what happens when that window becomes long. For an India-first model, long context is therefore not just a premium feature — it also recovers some of the effective document length lost when a language needs more tokens for the same content.

16 · the decision

What V5 has to decide

We should not end by pretending V5's attention architecture has already been chosen. V4 is finished, and its configuration gives us evidence — it does not automatically give us the V5 configuration. The frontier moved after those choices were made, the hardware changed, the kernels changed, and some of our own V4 choices were never ablated.

So the useful question is not what did V4 use? It is:

Which V4 decisions are now evidence,
which are merely defaults,
and what must be re-tested for V5?

This is a useful state to be in. We are not searching the entire architecture space from zero — we know the broad design pressures, and what remains is an experimental question about which mixture and which ratios give the best trade at V5's actual target.

We know the shape of the decision. We do not yet know the winning configuration. Getting to this shape is itself the part that took the field years; the remaining questions are narrow enough that well-designed proxy runs can actually settle them. This is also where the cohort contributes — the candidate techniques and ablations from these sessions are inputs into the V5 architecture review.

aside · chronology

The order we teach is not the order it happened

This session is arranged to build understanding: mechanism first, then its two bills, then each lever that reduces one of them. The actual research timeline interleaves very differently, and four of the inversions are worth knowing. 

2014        additive attention (Bahdanau)
2017 Jun    Transformer — scaled dot-product, multi-head, sinusoidal position   §2
2018        learned absolute position tables; relative position (Shaw)
2019 Jan    Transformer-XL — segment recurrence with stop-gradient             §14
2019 Apr    Sparse Transformer                                                 §7
2019 Nov    MQA — "One Write-Head is All You Need" (Shazeer)                   §11
2019 Nov    Compressive Transformer                                            §12
2020        linear attention — Transformers are RNNs, Performer, Linformer      §4
2021 Feb    fast-weight programmers — names add-only interference, delta rule  §5 §6
2021 Apr    RoPE (RoFormer)                                                    §8
2023        Position Interpolation → NTK-aware scaling → YaRN                  §9
2023 May    GQA (Ainslie et al.)                                               §11
2024        DeltaNet parallelised over sequence length; Gated DeltaNet          §6
2024        hybrid depth schedules — Griffin, Jamba, Samba                     §13
2025        Native Sparse Attention (DeepSeek)                                 §12
  • §14 is the oldest advanced idea, not the newest. Stop-gradient cross-segment recurrence is Transformer-XL, January 2019 — it predates linear attention, RoPE and GQA. V4's Memory Stream is that mechanism squeezed down to one vector.
  • §7 sparse came before §4–6 linear. Sparsity was the first response to the T² bill; deleting softmax came a year later.
  • §11 spans four years. MQA (2019) is earlier than everything in §4–§9; GQA (2023) is later. MQA sat largely ignored for three years until serving costs made it urgent.
  • §3's two bills were not simultaneous. Compute drove 2019–2020 research; the KV-cache bill only became dominant around 2022–2024 with serving at scale.

Where the session order is genuinely historical: §4 → §5 → §6 is exactly the argument of the 2021 fast-weight paper, in order. And §13's "you don't have to choose one" is not a synthesis invented for this course — it is where the field actually landed in 2024–25.

Evidence boundary. Everything dated above is public literature. The DroPE step in §9, and the LightningLM V4, DeepSeek-V4 and Qwen3.6 configurations quoted throughout, come from internal course record rather than published papers. The widgets mark those separately and do not simulate mechanisms the record does not specify.
