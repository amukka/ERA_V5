Nine cleaning strategies

Session 4 lays out an ordered pipeline — not a menu. Each stage depends on the one before it, and each one fixes a named defect from the V4 audit. Extraction (§2) is counted as Session 3 material and treated as given, which is why the count here is nine rather than ten.

Dataset picked: ai4bharat/sangraha verified/

Why Sangraha, not an instruction set

Sangraha is a genuine web crawl, so near-duplicates, mislabeled languages, PII and encoding damage are actually present and can be measured. Cleaning a synthetic instruction set means measuring your regex against your own generator.

The sovereign thread, for real

Sessions 3 and 4 both run an Indic thread — ZWJ/ZWNJ joiners, English-tuned filter bias, Indic PII false positives. A Telugu slice exercises all three against real Brahmic text rather than injected samples.

Telugu + English side by side

Drawing both verified/tel and verified/eng lets stage 3 measure filter bias directly: the same rules, the same corpus, one script-aware and one not.

Multi-shard by design

The slice is drawn from several shards so stage 5 can show what the session calls the systems problem: every shard passing its own local dedup while cross-shard duplicates survive.

Shards loaded

Deduplication: the mechanism, and why it needs one machine

Documents are shingled into word 5-grams, reduced to MinHash signatures, and bucketed by LSH bands. Only documents sharing a band are compared, and every candidate pair is verified with a true Jaccard score before anything is dropped.

Local passes vs. the global pass

Each shard was deduplicated on its own first — the way a student cleaning their own shard would. Then one global pass ran over the union of those already-clean shards.

Recall validation

Known near-duplicates, built by mutating real corpus documents, pushed through the same band-lookup and Jaccard-verification path the corpus pass uses.
